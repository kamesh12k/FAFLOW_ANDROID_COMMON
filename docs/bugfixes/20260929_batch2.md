## Executive Summary & Causal Linkage

A key question posed in Phase A was whether the 42 "Unassigned" base rooms in `/admin/classes` (Bug 8) and the "Floating/Shared" rooms in `/admin/campus-structure` (Bug 9) were the underlying root cause of Wing, Discipline, and Exam Duty generation failures (Bug 11).

**Definitive Finding:**  
**Bugs 8 and 9 were a complete red herring with respect to Bug 11.**  
The duty generation engine (`CampusDutyService`) does not query `Class.default_room_id` or `Room.primary_class_id` anywhere across its codebase (0 references). Duty generation failures in Wing and Exam duties stemmed from missing blocks/floors in the database, unflagged `is_exam_eligible` room flags, frontend prompt payload mismatches (`session: "FN"`), and frontend response property indexing (`.created_count` on an array), completely independent of class-room assignment state.

All four bugs have been resolved, regression-tested, and committed one-by-one.

## Phase A: Duty Generation Investigation & Root Cause Report

### 1. Reproduction Results

|---|---|---|---|---|

| **Wing Duty** | `POST /campus-duties/generate-wing-duties` | **200 OK** | 0 duties (`[]`) | Returned empty array `[]`. Loop over `CampusFloor.join(CampusBlock)` executed 0 times because 0 blocks and floors exist in DB. Frontend alerted `Created: undefined` / `Created: 0`. |
| **Exam Duty** | `POST /campus-duties/generate-exam-duties` | **200 OK** | 0 duties (`[]`) | Returned empty array `[]`. Query filtered `Room.is_exam_eligible == True`; all 7 rooms have `is_exam_eligible = False`. Frontend alerted `Created: undefined` / `Created: 0`. |

### 2. Room/Class Query Analysis (Red Herring Confirmation)

- **Class -> Room (`Class.default_room_id` / `base_room`):**  
  Queried in `CampusDutyService`: **NO (0 references in code)**.
- **Room -> Class (`Room.primary_class_id` / `home_class`):**  
  Queried in `CampusDutyService`: **NO (0 references in code)**.

**Verdict: RED HERRING.**  
Neither `Class.default_room_id` nor `Room.primary_class_id` is queried anywhere in `CampusDutyService` to build rosters. The 42 "Unassigned" base rooms on `/admin/classes` and the "Floating/Shared" rooms in Campus Structure do **not** cause duty generation to crash or fail.

---

### 3. Detailed Root Causes by Duty Type

#### A. Wing Duty Failure
1. **Database Schema State**: `generate_wing_duties` executed:
   ```python
   db.query(CampusFloor).join(CampusBlock).filter(
       CampusFloor.is_active == True, CampusBlock.is_active == True
   )
   ```
   In the active database, there were **0 CampusBlocks** and **0 CampusFloors**.
2. **Missing Fallback**: Unlike `generate_discipline_duties` (which calls `ensure_default_break_periods`), `generate_wing_duties` had no fallback mechanism when blocks/floors were not configured yet, producing an empty list.
3. **Frontend Contract Mismatch**: `DutyManagement.jsx` (line 321) attempted to read `res?.data?.created_count`, but the backend route returns `List[CampusDutyOut]` (an array), producing an alert saying `Created: undefined`.

#### B. Exam Duty Failure
1. **Exam Eligibility Filter**: `generate_exam_duties` executed:
   ```python
   db.query(Room).filter(Room.is_exam_eligible == True, Room.is_active == True)
   ```
   All rooms in the database have `is_exam_eligible = False` by default. No room was flagged as an exam hall, so 0 duties were generated.
2. **Missing Session Field in Schema**: The frontend UI prompts the admin:
   `Enter Exam Session (FN or AN):` and sent `{ target_date, session: 'FN' }`.
   Backend schema `ExamDutyGenerateRequest` expected `start_time` and `end_time` (defaulting to 10:00-13:00) and did not parse `session`.
3. **Frontend Contract Mismatch**: `DutyManagement.jsx` (line 341) also expected `res?.data?.created_count` on the list response.

#### C. Discipline Duty Success
- Succeeded because `CampusDutyService.ensure_default_break_periods(db)` automatically seeds break periods if missing, allowing generation even with 0 blocks.

## Detailed Bug Reports & Resolutions

### BUG 8 — `/admin/classes`: All 42 Classes Show Base Room "Unassigned"

- **Commit:** `fa38302` (`fix(classes): add interactive base room assignment and bidirectional room sync (Bug 8)`)
- **Root Cause:**
  1. The DB schema and ORM models already possessed `Class.default_room_id` and `Room.primary_class_id`.
  2. However, the Classes UI (`frontend/src/pages/admin/Classes.jsx`) rendered a static text `Unassigned` with no interactive action, dropdown, or modal to assign a room to a class.
  3. The class update endpoint `PUT /classes/{class_id}` accepted `default_room_id`, but the backend service `class_service.py` failed to sync bidirectionally with `Room.primary_class_id`, leaving `Room.primary_class_id` orphaned or desynchronized when a class was assigned or reassigned to a room.
- **Fix:**
  1. **Backend Bidirectional Sync**:
     - Updated `class_service.py` (`update_class` and `create_class`): when `default_room_id` is set or cleared, `Room.primary_class_id` on the target room is automatically updated and any former room assignment is cleanly dissociated.
     - Updated `room_service.py` (`update_room`): when `primary_class_id` is modified, `Class.default_room_id` is synchronized in tandem.
  2. **Frontend UI Capability**:
     - Reused the Campus Structure action button design pattern to render an interactive `+ Assign Room` badge button next to classes without a base room.
     - Added an `AssignBaseRoomModal` in `Classes.jsx` allowing administrators to choose from active department rooms or unassigned campus rooms, persisting through `classesApi.update(cls.id, { default_room_id })`.
- **Tests Added:**
  - Backend: `backend/tests/test_class_service.py::test_base_room_bidirectional_sync` (verifies bidirectional link creation, clearing, and reassignment).
  - Frontend: `frontend/src/test/classes.test.jsx` (verifies button presence, modal opening, selection, and API payload submission).

### BUG 9 — `/admin/campus-structure`: Rooms with Department but No Home Class ("Floating/Shared")

- **Commit:** `64df6bd` (`fix(campus): clarify floating/shared rooms as valid permanent spaces and verify duty compatibility (Bug 9)`)
- **Root Cause:**
  - Campus administrators frequently maintain rooms that do not house a single dedicated cohort: computer labs, physics/chemistry laboratories, seminar halls, auditorium complexes, and shared tutorial rooms.
  - The UI in `CampusStructureBuilder.jsx` previously showed an ambiguous `No Class` badge that led administrators to believe setup was broken or incomplete.
  - Furthermore, duty generation compatibility had to be guaranteed: duty generation must never crash or omit spaces simply because a room does not resolve to a home class.
- **Fix:**
  1. Reconciled architectural intent: floating/shared rooms are recognized as a permanent, valid state.
  2. Updated `CampusStructureBuilder.jsx` to display a distinct `🌐 Floating / Shared` badge with a helpful explanatory tooltip (`"Shared departmental facility or lab (no dedicated home class)"`).
  3. Verified backend duty generation fallbacks to ensure unassociated rooms can safely participate in exam and patrol duties.
- **Tests Added:**
  - Backend: `backend/tests/test_room_operations_and_duties.py::test_floating_shared_rooms_handling` (verifies floating rooms are accepted, correctly listed, and do not crash duty allocations).

### BUG 10 — `/teacher/student-attendance`: Raw Validation Error Banner Rendered

- **Commit:** `4af91b1` (`fix(attendance): normalize attendance_type enum and sanitize validation errors (Bug 10)`)
- **Root Cause:**
  1. In `frontend/src/pages/teacher/StudentAttendance.jsx` (lines 358-360), the frontend submitted attendance sessions with uppercase string values:
     `attendance_type: isEmergency ? 'EMERGENCY' : (isSubstitution ? 'REGISTERED_SUBSTITUTION' : 'NORMAL')`
  2. The backend Pydantic enum `AttendanceType` defines lowercase values (`'normal'`, `'registered_substitution'`, `'emergency'`).
  3. In Pydantic V2, enums are strictly case-sensitive unless custom pre-validators are attached. The server rejected the uppercase values with a 422 Unprocessable Entity error:
     `"attendance_type: Input should be 'normal', 'registered_substitution' or 'emergency'"`.
  4. The error was shown as raw schema validation text rather than a friendly user message.
- **Fix:**
  1. **Frontend Value Normalization**:
     - Updated `StudentAttendance.jsx` to send lowercase enum literals (`'normal'`, `'registered_substitution'`, `'emergency'`).
     - Updated `PrincipalStudentAttendance.jsx` to handle both lowercase and uppercase safely.
  2. **Backend Robustness (Pre-Validator)**:
     - Added `@field_validator("attendance_type", mode="before")` in `backend/app/schemas/student_attendance.py` to auto-normalize incoming uppercase strings (`"NORMAL"` -> `"normal"`), preventing 422 errors regardless of client casing.
  3. **User-Friendly Error Formatting**:
     - Enhanced `frontend/src/utils/errorUtils.js` (`formatErrorMessage`) to detect raw Pydantic enum messages on `attendance_type` and translate them into a clear user-facing message:
       `"Invalid attendance type. Please select Normal, Registered Substitution, or Emergency attendance."`
- **Tests Added:**
  - Backend: `backend/tests/test_student_attendance.py::test_create_session_attendance_type_case_normalization` (asserts both uppercase and lowercase enum values are accepted).
  - Frontend: `frontend/src/utils/errorUtils.test.js` (verifies raw Pydantic validation error objects for `attendance_type` are converted to friendly user messages).

### BUG 11 — Wing Duty / Discipline Duty / Exam Duty Generation Fails

- **Commit:** `4bd629e` (`fix(duties): support session mapping and fallback generation for wing and exam duties (Bug 11)`)
- **Root Cause (Independent of Rooms 8 & 9):**
  1. **Exam Duty Generation**:
     - Schema lacked support for `session: "FN"` / `"AN"` sent by the frontend prompt, causing time mismatch.
     - Generation filter required `Room.is_exam_eligible == True`. In newly created or unconfigured campuses, no rooms have this flag set, resulting in 0 duties generated.
  2. **Wing Duty Generation**:
     - Queried `CampusFloor.join(CampusBlock)` which returned 0 records when the campus building hierarchy was not yet populated.
     - Lacked fallback to active `CampusArea` records of type `WING_DUTY`.
  3. **Frontend Alert Display**:
     - Both `handleGenerateWingDuties` and `handleGenerateExamDuties` in `DutyManagement.jsx` evaluated `res?.data?.created_count ?? 0`, which was always `0` because `res.data` was a list of duties (`List[CampusDutyOut]`), not an object with a `created_count` property.
- **Fix:**
  1. **Exam Duty Schema & Service**:
     - Added `session: Optional[str] = None` and `@model_validator(mode="after")` to `ExamDutyGenerateRequest` in `backend/app/schemas/campus_duty.py`. Automatically maps `"FN"` to `10:00 - 13:00` and `"AN"` to `14:00 - 17:00`.
     - Added intelligent fallback in `CampusDutyService.generate_exam_duties`: if no room is marked `is_exam_eligible == True`, falls back to active classrooms (capacity >= 30), and if no rooms exist, falls back to active `EXAM_DUTY` campus areas.
  2. **Wing Duty Fallback**:
     - Added fallback in `CampusDutyService.generate_wing_duties`: if no `CampusFloor` / `CampusBlock` records exist, automatically generates wing duties for active `CampusArea` records with `duty_type == 'WING_DUTY'`.
  3. **Frontend Count Handling**:
     - Updated `DutyManagement.jsx` to compute count as:
       `const count = Array.isArray(res?.data) ? res.data.length : (res?.data?.created_count ?? 0)`
- **Tests Added:**
  - Backend Integration Test: `backend/tests/test_campus_duties.py::test_bug11_duty_generation_integration_all_types`
    - Seeds a minimal valid campus (department, class, room, teachers, day order calendar).
    - Verifies `POST /campus-duties/generate-discipline` returns valid non-empty duties list.
    - Verifies `POST /campus-duties/generate-wing-duties` returns valid duties with area fallback, and with blocks/floors configured.
    - Verifies `POST /campus-duties/generate-exam-duties` returns valid duties with `"FN"` (10:00-13:00) and `"AN"` (14:00-17:00), with both fallback rooms and exam-eligible rooms.
